# 系统需求与架构设计

## 四、系统总体架构

### 4.1 架构设计目标

系统整体采用模块化设计思路，作为 Windows 桌面端应用运行，将视频输入、视觉检测、特征分析、疲劳判断、预警反馈及界面展示进行职责划分。

各模块围绕统一的检测流程进行协作，形成完整的疲劳检测与预警系统。

### 4.2 核心模块划分

#### 模块一：视频采集模块

**模块职责：**

负责获取摄像头或测试视频中的图像数据，并为视觉分析模块提供输入。

**能力要求：**

- 支持实时摄像头输入。
- 支持必要的测试视频输入。
- 能够反馈视频采集状态。
- 满足实时检测所需的基础性能要求。

#### 模块二：人脸检测模块

**模块职责：**

基于 YOLO 系列模型识别视频中的驾驶员人脸，为面部特征提取提供人脸区域信息。

**能力要求：**

- 完成驾驶员人脸检测。
- 支持连续视频场景下的检测。
- 对检测不到人脸等异常情况进行合理处理。
- 为后续模块提供稳定的检测结果。

该模块是项目中 YOLO 技术应用的主要体现，也是后续实验评估的重要对象。

#### 模块三：面部特征提取模块

**模块职责：**

从检测到的人脸区域中提取与疲劳行为相关的面部特征。

**主要分析对象：**

- 眼部特征。
- 面部关键点。
- 头部姿态特征。
- 其他可用于疲劳分析的辅助特征。

**能力要求：**

- 提供疲劳分析所需的关键特征。
- 具备一定的特征有效性判断能力。
- 与人脸检测模块保持明确的职责边界。

#### 模块四：疲劳分析模块

**模块职责：**

根据面部特征及其随时间的变化情况，分析驾驶员是否存在潜在疲劳行为。

**主要分析方向：**

- 眼睛闭合状态。
- 连续闭眼行为。
- PERCLOS 疲劳指标。
- 头部异常姿态。
- 重复点头等辅助疲劳特征。

**能力要求：**

- 能够分析单一疲劳特征。
- 能够分析随时间变化的疲劳行为。
- 为疲劳风险判断提供有效依据。

#### 模块五：疲劳风险判断模块

**模块职责：**

综合疲劳分析结果，判断驾驶员当前疲劳风险程度。

**初步状态划分：**

- 正常状态。
- 轻度疲劳风险。
- 严重疲劳风险。
- 检测不可用或状态未知。

**能力要求：**

- 综合不同疲劳指标。
- 尽量减少正常驾驶行为引起的误报。
- 保持判断结果的合理性和可解释性。
- 区分疲劳风险和检测异常，避免混淆。

#### 模块六：预警模块

**模块职责：**

根据疲劳风险判断结果向驾驶员发出警报。

**能力要求：**

- 支持视觉警告。
- 支持声音警报。
- 根据不同风险程度进行差异化提醒。
- 避免重复、无意义的频繁警报。
- 能够随风险状态变化调整警报状态。

#### 模块七：可视化与记录模块

**模块职责：**

负责系统的人机交互、检测结果展示及必要的数据记录。

**能力要求：**

- 展示摄像头实时画面。
- 展示关键疲劳检测指标。
- 展示当前疲劳风险等级。
- 提供检测启动和停止操作。
- 展示警报信息。
- 保存及查看必要的历史预警记录。

### 4.3 模块协作关系

整体按照以下业务流程运行：

1. 视频采集模块获取驾驶员图像。
2. 人脸检测模块定位驾驶员面部区域。
3. 面部特征提取模块获得疲劳分析所需的信息。
4. 疲劳分析模块对眼部及头部行为进行分析。
5. 疲劳风险判断模块确定当前风险程度。
6. 预警模块根据风险程度触发对应反馈。
7. 可视化模块持续更新系统运行状态及检测结果。

各模块的具体接口、数据结构及内部实现不在本规划文档中定义。

可以在总体规划文档的\*\*第四章「系统总体架构」\*\*中补充 `4.4 模块关联关系`。

这里用字符树表示模块的层级、职责和关联关系，不涉及具体实现。

### 4.6 模块关联说明

| 上游模块   | 下游模块   | 关联内容           |
| ------ | ------ | -------------- |
| 视频采集   | 人脸检测   | 提供视频图像         |
| 人脸检测   | 面部特征提取 | 提供驾驶员人脸区域      |
| 面部特征提取 | 疲劳分析   | 提供眼部、头部特征      |
| 疲劳分析   | 风险判断   | 提供疲劳行为分析结果     |
| 风险判断   | 预警模块   | 提供风险等级与警报依据    |
| 各检测模块  | 可视化与记录 | 提供视频、指标和状态信息   |
| 预警模块   | 可视化与记录 | 提供警报事件和状态      |
| 系统管理   | 各业务模块  | 管理运行状态和系统配置    |
| 可视化与记录 | 系统管理   | 提交用户启动、停止等操作请求 |

架构设计原则：

检测流程采用单向的数据处理关系，各模块只负责自身职责。疲劳分析不直接操作界面，YOLO 人脸检测不直接判断疲劳，疲劳风险判断不直接负责声音播放。

可视化与系统管理属于横向支撑模块，不应被设计成检测算法链路中的必经处理环节。

这样既能在总体规划中清晰表达各模块的关联关系，也能为后续详细设计提供明确的模块边界。

## 五、功能需求规划

### 5.1 核心功能

以下功能是项目完成的基本要求：

| 编号 | 功能 | 目标 |
|---|---|---|
| F01 | 视频采集 | 实时获取驾驶员面部画面 |
| F02 | YOLO 人脸检测 | 在视频中检测驾驶员人脸 |
| F03 | 面部特征提取 | 提取眼部等关键面部特征 |
| F04 | 闭眼行为检测 | 识别眼睛闭合及持续闭眼行为 |
| F05 | PERCLOS 分析 | 评估一定时间范围内的闭眼情况 |
| F06 | 疲劳风险判断 | 判断是否存在疲劳风险 |
| F07 | 声光预警 | 对异常行为提供声音和视觉反馈 |
| F08 | 实时结果展示 | 展示检测画面及系统状态 |

### 5.2 增强功能

在核心功能完成后，优先考虑以下功能：

| 编号 | 功能 | 目标 |
|---|---|---|
| F09 | 头部姿态分析 | 辅助判断低头、点头等行为 |
| F10 | 疲劳风险分级 | 区分不同程度的疲劳风险 |
| F11 | 历史记录管理 | 记录和查看疲劳预警事件 |
| F12 | 视频文件检测 | 便于测试、复现与实验分析 |
| F13 | 自适应检测参数 | 降低个体差异对检测结果的影响 |

### 5.3 可选扩展功能

以下功能不作为项目的必要交付条件：

- 打哈欠行为检测。
- 多种 YOLO 模型对比。
- 不同疲劳检测策略的对比实验。
- 检测性能优化。
- 更丰富的疲劳状态可视化。
- 面向特殊环境的鲁棒性改进。

扩展功能应以核心系统稳定运行为前提，不得影响必要功能的交付。

## 六、非功能需求

### 6.1 实时性

系统应能够持续处理摄像头视频，并在检测到异常疲劳行为后及时反馈。

具体帧率和报警响应时间目标应结合运行环境及测试结果确定。

### 6.2 准确性

系统应具备基本的疲劳相关行为识别能力，并尽量降低误报和漏报。

检测准确性需要通过实验数据进行评估，不预先假定某一准确率指标一定能够达到。

### 6.3 稳定性

系统在正常使用过程中应能够持续运行。

对于摄像头不可用、人脸丢失、检测异常等情况，应有合理的状态反馈，避免异常导致整个程序失效。

### 6.4 易用性

软件界面应简单清晰，用户能够直接理解当前检测状态、疲劳风险及报警信息。

### 6.5 可维护性

系统应保持合理的模块划分，便于后续替换检测模型、调整疲劳判断策略及扩展功能。

### 6.6 可验证性

系统应能够通过测试视频、模拟行为及其他合理的实验方式验证各项功能。

对于尚未验证的特殊场景和安全能力，不应做出超出实验结果的结论。
