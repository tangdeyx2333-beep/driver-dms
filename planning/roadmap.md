# 驾驶疲劳检测与预警系统：建设路线

> 状态：独立评审通过，待用户确认。本路线依据已确认的 [系统总览](overview.md) 制定；它确定需求范围与建设顺序，不代表任何单项需求已获编码授权。各需求的具体行为和验收细则留待对应 Spec 确认。

## 1. 建设策略

先形成可运行、可观察的画面输入与 YOLO 人脸定位，再接入本地可重复实验输入。随后建立眼部行为、PERCLOS、基础风险和声光预警的完整闭环；闭环稳定后增加头部姿态辅助依据和风险分级。每项需求独立经过 Spec、评审、用户确认、Task/Test 规划、评审、实现授权、验证与验收。实验和论文材料随各阶段积累，以真实结果收束。

运行时主链路保持本地离线，YOLO 实际承担人脸定位；实验输入和摄像头输入进入同一分析链路。每阶段先交付可检查的结果，再作为后续阶段的依据。头部姿态失效时不得凭此提高风险；输入、人脸或眼部基础分析失效时须呈现检测不可用并解除过期预警。

## 2. 需求清单与依赖

| 编号 | 需求 | 范围与阶段成果 | 前置依赖 | 状态 |
|---|---|---|---|---|
| R01 | 视频输入与运行控制 | 选择摄像头、显示画面、启动和停止；输入异常有明确状态 | 无 | 必做，待 Spec |
| R02 | YOLO 人脸定位 | 在连续画面中标示目标人脸；未检出或结果无效时呈现检测不可用 | R01 | 必做，待 Spec |
| R06 | 可重复实验输入 | 同一本地材料可重复送入现有检测链路，保留来源与使用条件 | R01、R02 | 必做，待 Spec |
| R03 | 眼部特征与闭眼行为 | 显示有效眼部状态，识别持续闭眼；眼部依据不足时停止疲劳结论 | R02；实验核对使用 R06 | 必做，待 Spec |
| R04 | PERCLOS 与基础风险判断 | 在观察窗口内统计闭眼比例，区分正常、基础疲劳风险与检测不可用，并呈现依据 | R03；验证使用 R06 | 必做，待 Spec |
| R05 | 声光预警与实时展示 | 风险变化驱动视觉和声音提醒；恢复、停止或检测失效时同步更新反馈 | R04 | 必做，待 Spec |
| R07 | 头部姿态辅助分析 | 有效姿态作为辅助依据；无效姿态不凭空提高风险 | R03、R04、R05 | 必做，待 Spec |
| R08 | 轻度与严重风险分级 | 区分正常、轻度、严重与检测不可用，预警反馈与等级一致 | R04、R05、R07 | 必做，待 Spec |

R06 的编号沿用原开发总览，建设顺序早于 R03；编号表示既有需求标识，不表示严格开发次序。R03 的实现可基于 R02 启动，但其重复核对须使用已完成的 R06。具体目录在 Roadmap 确认并移交需求时按 `planning/requirements/<编号-名称>/` 建立；此处不提前创建 Spec、Task 或 Test。

## 3. 阶段依赖逻辑树

```text
第一阶段：建立输入与人脸定位
+-- R01 视频输入与运行控制
+-- R02 YOLO 人脸定位（依赖 R01）
+-- 可观察：启动、停止、画面、目标人脸区域或不可用状态
|
`-- 第二阶段：建立可重复验证输入
    +-- R06 可重复实验输入（依赖 R01、R02）
    +-- 可观察：同一材料重复进入既有检测链路
    |
    `-- 第三阶段：建立眼部风险与预警闭环
        +-- R03 眼部特征与闭眼行为（开发依赖 R02；使用 R06 核对）
        +-- R04 PERCLOS 与基础风险判断（依赖 R03）
        +-- R05 声光预警与实时展示（依赖 R04）
        +-- 可观察：有效眼部依据 -> 风险 -> 声光反馈；失效时解除过期预警
        |
        `-- 第四阶段：增强必做判断能力
            +-- R07 头部姿态辅助分析（依赖稳定的眼部预警闭环）
            +-- R08 轻度与严重风险分级（依赖 R04、R05、R07）
            +-- 可观察：分级依据及与等级一致的预警；姿态失效可降级
            |
            `-- 最终评价与交付
                +-- 真实样本、人工依据、误报漏报和响应表现分析
                `-- 运行说明、论文与演示材料；用户最终验收
```

这棵树表达计划建设顺序；单项需求的开发前置依赖以第 2 节需求表为准，不能把阶段排列误读为每项需求的硬性开发依赖。它也不能替代系统总览中的逐帧运行逻辑。实验准备和记录贯穿各阶段；最终评价基于已交付能力，不将论文写作视作业务功能的前置条件。

## 4. 系统能力覆盖与阶段验收

| Overview 能力 | 建设需求 | 阶段可检查结果 |
|---|---|---|
| 输入与运行控制 | R01、R06 | 摄像头或本地固定材料可进入同一流程；停止、异常和输入状态可见 |
| YOLO 人脸定位 | R02 | YOLO 定位的人脸区域进入后续分析；无效结果可见 |
| 面部特征提取 | R03、R07 | 眼部基础特征及头部辅助特征具有有效性信息 |
| 疲劳行为分析 | R03、R04、R07 | 闭眼、持续闭眼、PERCLOS 和姿态依据可以追溯到有效画面 |
| 风险判断 | R04、R08 | 基础风险逐步扩展为正常、轻度、严重与检测不可用 |
| 声光预警与展示 | R01、R02、R04、R05、R08 | 画面、依据、状态和反馈随当前结果更新，失效或停止不沿用旧警报 |
| 实验与评价 | R06 及各需求验证；最终评价里程碑 | 固定输入、人工标注依据、实际输出与评价记录可核查 |

各需求完成时在其 `test.md` 记录实际冒烟步骤、结果和证据。R06 完成后核对固定材料的重复输入。R08 完成后，在安全静止环境中进行功能与效果实验，区分模拟疲劳行为与真实生理疲劳；记录输入来源、标注依据、误报漏报、响应与运行表现。最终交付运行说明、实验分析、论文和演示材料。未执行或未达到目标的项目如实列明，不能以计划值代替实测。

## 5. 增强范围与验证关口

R09 历史预警记录、R10 个体自适应参数属于候选增强能力，当前不承诺建设。只有用户另行确认纳入范围后，才修订本路线并启动相应 Spec。历史记录不作为声光预警闭环的前置条件。

| 关口 | 应核查事项 | 处理原则 |
|---|---|---|
| R02 前 | 候选 YOLO 人脸模型及权重的来源、许可、目标设备上的效果与速度 | 现有开发总览建议优先验证 yolov5-face；候选不等于定案 |
| R03 前 | YOLO 人脸区域与本地关键点工具的衔接、目标人脸规则和失效识别 | 可优先验证 MediaPipe Face Landmarker；不得绕过 YOLO 主链路 |
| R04、R08 前 | 采样、时间窗口、阈值、部分特征失效时的降级及风险切换 | 由对应 Spec 定义可验收规则，不在路线图虚设数值 |
| R05 前 | 界面响应、声音提醒与解除、异常状态呈现 | PySide6 是候选；依据目标设备验证 |
| 最终评价前 | 实验材料许可、隐私、人工标注和指标口径 | 仅使用可追溯的真实执行记录 |

目标硬件与摄像头、多人画面的目标选择、R06 是否提供普通用户的视频文件入口、报警重复与解除规则，仍需在对应 Spec 中确认。若模型许可、性能或接口衔接不能满足系统总览，应记录验证证据，回到相应阶段评估替代方案；涉及已确认范围或关键行为的变化须重新提交用户确认。
