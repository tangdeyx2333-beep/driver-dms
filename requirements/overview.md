# 驾驶疲劳检测与预警系统：开发总览

> 本文档确定开发顺序、阶段目标和技术选型方向。各项功能的交互细节、判断规则及验收条件将在对应 `spec.md` 中确认；确认 Spec 后才编写 `task.md` 与 `test.md`。本文档不是实现授权，也不代表功能已经完成。

## 1. 目标与边界

开发一套运行于 Windows 个人计算机的桌面原型：从普通摄像头取得画面，使用 YOLO 检测人脸，分析眼部疲劳特征，判断风险，并在界面上展示结果和发出声光提醒。系统用于毕业设计研究、静止环境下的实验与演示，不承担真实道路安全保障。

系统按本地离线软件设计：摄像头或本地测试视频提供画面，模型权重保存在本机，视频读取、人脸定位、关键点提取、疲劳判断与预警均在本机完成。核心检测与演示不依赖外部云 API、在线推理服务或上传视频；安装依赖和获取经许可的模型文件属于开发准备，不改变运行时离线要求。

最终课题必做范围包括：原规划 F01—F08 的检测预警闭环、F09 头部姿态辅助分析、F10 轻度与严重风险分级，以及可重复实验输入、实验分析和论文配套材料。头部姿态与风险分级安排在眼部检测闭环稳定之后。历史预警记录和自适应参数作为增强功能，不计入当前必做范围。车辆控制、车载通信、身份识别、云端部署和从零训练深度学习网络不在本项目范围。

## 2. 开发顺序

每项需求均按项目规范独立完成 Spec、评审、用户确认、Task/Test 规划、评审、授权实现、验证和验收。以下是需求路线，不是已经批准的实现任务。

| 顺序 | 需求编号与名称 | 对应原规划 | 可观察的阶段成果 | 前置依赖 | 当前状态 | 主要技术或知识 | 后续需求文档位置 |
|---|---|---|---|---|---|---|---|
| 1 | R01 视频输入与运行控制 | F01、F08 的基础部分 | 桌面程序可选择摄像头、显示画面并启动/停止检测；输入异常有状态提示 | 无 | 必做；待 Spec | Python、OpenCV、桌面事件处理 | `requirements/features/R01-video-input/` |
| 2 | R02 YOLO 人脸定位 | F02 | 在连续画面中标示人脸；未检出时明确显示不可用状态 | R01 | 必做；待 Spec | YOLO 人脸模型、推理、坐标映射 | `requirements/features/R02-face-detection/` |
| 3 | R06 可重复实验输入 | F12 的实验支撑部分 | 同一测试画面可重复输入检测链路，供后续指标核对；是否提供界面入口由 Spec 决定 | R01、R02 | 必做；待 Spec | 视频文件读取或等效固定输入、时间戳 | `requirements/features/R06-repeatable-input/` |
| 4 | R03 眼部特征与闭眼行为 | F03、F04 | 展示有效眼部状态，并识别持续闭眼；关键点无效时不输出疲劳结论 | R02；实验核对依赖 R06 | 必做；待 Spec | 面部关键点、EAR、时间连续性 | `requirements/features/R03-eye-state/` |
| 5 | R04 PERCLOS 与基础风险判断 | F05、F06 | 在规定观察窗口内统计闭眼比例，区分正常、疲劳风险和检测不可用并显示触发依据 | R03 | 必做；待 Spec | 时序窗口、PERCLOS、状态规则 | `requirements/features/R04-fatigue-risk/` |
| 6 | R05 声光预警与实时展示 | F07、F08 | 风险触发时给出视觉与声音提醒；状态变化后界面同步更新 | R04 | 必做；待 Spec | PySide6、音频反馈、界面状态同步 | `requirements/features/R05-alert-ui/` |
| 7 | R07 头部姿态辅助分析 | F09 | 对有效头部姿态给出辅助判断信息；无法取得有效姿态时不凭空提高风险 | R03—R05 的眼部闭环 | 必做；待 Spec | 头部姿态估计、时序分析 | `requirements/features/R07-head-pose/` |
| 8 | R08 轻度与严重风险分级 | F10 | 明确区分正常、轻度风险、严重风险与检测不可用，预警反馈与等级一致 | R04、R05、R07 | 必做；待 Spec | 多特征规则、状态转换 | `requirements/features/R08-risk-levels/` |

核心依赖链为：**视频输入 → YOLO 人脸定位 → 可重复实验输入 → 眼部特征 → PERCLOS 与基础风险 → 预警展示 → 头部姿态辅助分析 → 风险分级**。实验输入在 R02 后接入已有检测链路，供后续需求反复核对。每一步先形成可检查的输出，再供下一步消费。界面在早期只需承载视频和状态，最终呈现规则在对应 Spec 中确定。

**贯穿式验证与最终交付里程碑：**

| 阶段 | 产物 | 完成条件 |
|---|---|---|
| 各需求验收时 | 对应 `test.md` 中的冒烟步骤、实际结果和证据 | 记录真实执行情况；未执行或失败的项目明确标出 |
| R06 建成后 | 本地固定测试输入及来源、使用条件说明 | 同一画面能够在本机重复送入检测链路，实验人员可核对输入一致性 |
| R08 建成后 | 实验方案、样本与人工标注依据、检测结果、误报漏报及响应表现统计 | 评价指标口径明确，结果可由输入和记录追溯；未达目标的场景如实列出 |
| 最终交付时 | 运行说明、实验分析、论文及配套演示材料 | 文档与实际实现和实验结果一致，形成可供用户验收的交付包 |

这些是跨需求的验证和交付工作，不单列为业务需求，也不替代各项需求的 Spec、Task、Test 和验收。论文写作与实验准备可随开发同步进行，最终结论必须以真实执行结果为依据。

## 3. 增强功能

| 编号 | 增强功能 | 对应原规划 | 建议进入条件 | 当前状态 |
|---|---|---|---|---|
| R09 | 历史预警记录 | F11 | 记录字段、保存期限和查看方式已明确 | 增强；暂不承诺 |
| R10 | 自适应检测参数 | F13 | 已测得固定参数在不同个体间的偏差 | 增强；暂不承诺 |

原文档对头部姿态、风险分级和历史记录的定位不一致。用户现已确认：头部姿态和风险分级属于最终必做；历史预警记录留在增强范围。可重复实验输入属于必做支撑能力，普通用户是否能从界面选择视频文件在 R06 的 Spec 中确定。

## 4. 技术选型方向与验证关口

| 领域 | 当前方向 | 选型状态 | 在对应需求中必须验证的事项 |
|---|---|---|---|
| 运行环境 | Windows 个人计算机、普通摄像头与本地模型文件 | 本地离线运行已明确；硬件规格待确定 | 摄像头兼容性、运行资源、断网时核心流程可用性 |
| 语言与视频处理 | Python、OpenCV | 总体规划初选 | 摄像头读取、画面连续性、异常恢复 |
| 人脸检测 | 优先验证 yolov5-face | 用户已同意优先验证该候选；**YOLO 必须在主链路中实际定位人脸**，模型与权重尚未定案 | 仓库代码的 GPL-3.0 使用条件、权重来源与许可、Windows 目标设备的检测效果和推理速度 |
| 面部关键点 | 优先验证本地运行的 MediaPipe Face Landmarker Python 库 | 用户已同意优先验证该候选，尚未完成本项目实测；不调用外部服务 | 将 YOLO 定位的人脸区域交给关键点模块时的坐标与图像格式衔接、关键点稳定性、失效识别 |
| 疲劳指标 | EAR、持续闭眼、PERCLOS | 指标方向已在规划中列出；参数未定 | 采样方式、观察窗口、阈值及正常眨眼区分 |
| 桌面界面 | PySide6 | 候选方案 | 视频刷新与推理并行时的界面响应、异常反馈 |
| 本地记录 | SQLite | 仅在 R09 纳入范围时选用 | 记录字段、查询与数据保存规则 |
| 实验材料 | 测试视频或标注样本，必要时使用 CVAT | 工具与数据来源待验证 | 使用许可、标注规则、可重复性、隐私处理 |

本轮确认的是优先验证 yolov5-face 与 MediaPipe 的组合，不等于实测通过，也不构成将开源代码移入项目的授权。验证时应保持 YOLO 人脸定位为关键点提取的上游输入，避免关键点模块绕过 YOLO 独立完成人脸定位。若权重许可、接口衔接、Windows 性能或失效处理不能满足需求，应记录证据并重新评估替代的 YOLO 人脸模型或关键点方案，再提交用户决定是否复用。

这里的“接口衔接”指本地程序内部模块间的数据传递；MediaPipe 是安装在本机的 Python 库，不是需要网络请求的第三方 API。后续 Spec 和实现不得把云端接口、在线账号或视频上传设为核心功能的运行条件。

在 R02 的 Spec 前，应查明候选模型和权重的来源、许可及使用条件；在 R03/R04 前，明确人脸丢失、关键点无效、画面中多人时如何处理；在最终实验前，确定测试场景、人工标注依据和指标计算口径。准确率、帧率、报警响应时间及阈值不得凭规划文件虚设为已达到的数值，应根据目标设备和样本完成技术验证后写入对应 Spec。

## 5. 范围决策与当前限制

1. **范围已确认：**R01—R08 为最终必做，其中 R06 为可重复实验输入，R07/R08 在眼部闭环后实施；R09/R10 为增强功能。
2. **待各需求 Spec 明确：**摄像头与目标设备、多人画面处理、风险状态规则、声音行为、检测阈值、实验验收口径，以及 R06 是否提供普通用户界面入口。
3. **仓库条件：**项目目录已有独立 `.git` 仓库，`master` 已有提交并跟踪 `origin/master`；目前未发现业务源码。进入单项需求开发前，仍需按 `AGENTS.md` 检查工作区与最新 `master`，再创建对应需求分支；不得擅自合并或推送。
