# 驾驶疲劳检测与预警系统：开发总览（待确认）

> 本文档确定开发顺序、阶段目标和技术选型方向。各项功能的交互细节、判断规则及验收条件将在对应 `spec.md` 中确认；确认 Spec 后才编写 `task.md` 与 `test.md`。本文档不是实现授权，也不代表功能已经完成。

## 1. 目标与边界

开发一套运行于 Windows 个人计算机的桌面原型：从普通摄像头取得画面，使用 YOLO 检测人脸，分析眼部疲劳特征，判断风险，并在界面上展示结果和发出声光提醒。系统用于毕业设计研究、静止环境下的实验与演示，不承担真实道路安全保障。

首轮开发围绕原规划的 F01—F08 建立完整链路。F09—F13 作为后续候选需求，是否纳入最终交付以用户确认的范围和技术验证结果为准。车辆控制、车载通信、身份识别、云端部署和从零训练深度学习网络不在本项目范围。

## 2. 开发顺序

每项需求均按项目规范独立完成 Spec、评审、用户确认、Task/Test 规划、评审、授权实现、验证和验收。以下是需求路线，不是已经批准的实现任务。

| 顺序 | 需求编号与名称 | 对应原规划 | 可观察的阶段成果 | 前置依赖 | 当前状态 | 主要技术或知识 | 后续需求文档位置 |
|---|---|---|---|---|---|---|---|
| 1 | R01 视频输入与运行控制 | F01、F08 的基础部分 | 桌面程序可选择摄像头、显示画面并启动/停止检测；输入异常有状态提示 | 无 | 待确认 | Python、OpenCV、桌面事件处理 | `requirements/features/R01-video-input/` |
| 2 | R02 YOLO 人脸定位 | F02 | 在连续画面中标示人脸；未检出时明确显示不可用状态 | R01 | 待确认 | YOLO 人脸模型、推理、坐标映射 | `requirements/features/R02-face-detection/` |
| 3 | R03 眼部特征与闭眼行为 | F03、F04 | 展示有效眼部状态，并识别持续闭眼；关键点无效时不输出疲劳结论 | R02 | 待确认 | 面部关键点、EAR、时间连续性 | `requirements/features/R03-eye-state/` |
| 4 | R04 PERCLOS 与风险判断 | F05、F06 | 在规定观察窗口内统计闭眼比例，显示风险状态及触发依据 | R03 | 待确认 | 时序窗口、PERCLOS、状态规则 | `requirements/features/R04-fatigue-risk/` |
| 5 | R05 声光预警与实时展示 | F07、F08 | 风险触发时给出视觉与声音提醒；状态变化后界面同步更新 | R04 | 待确认 | PySide6、音频反馈、界面状态同步 | `requirements/features/R05-alert-ui/` |

依赖链为：**视频输入 → YOLO 人脸定位 → 眼部特征 → PERCLOS 与风险 → 预警展示**。每一步先形成可检查的输出，再供下一步消费。界面在早期只需承载视频和状态，最终呈现规则在 R05 的 Spec 中确定。

**贯穿式验证与最终交付里程碑：**每项需求在各自的 `test.md` 中记录实际冒烟验证结果；到核心链路形成后，汇总可复现场景下的人脸检测、疲劳判断、响应表现和限制，整理运行说明、实验材料与论文所需证据。这是跨需求的验证及交付工作，不单列为业务需求，也不替代各项需求的 Spec、Task、Test 和验收。

原文档对头部姿态、风险分级和历史记录的定位不一致：总览与阶段规划将其写入项目范围，功能表将其列为增强功能。在用户确认之前，本文档不将 R06—R10 计入首轮必做承诺。

**视频文件输入建议：**为了让同一段画面能重复运行、比较参数与核对误报，建议将 R09 提前到 R02 完成之后、R03 开始之前实施，作为实验支撑需求。是否将其前置，以及是否提供给普通用户直接操作，仍须用户决定；在范围确认前不改动 R01—R05 的承诺。

## 4. 技术选型方向与验证关口

| 领域 | 当前方向 | 选型状态 | 在对应需求中必须验证的事项 |
|---|---|---|---|
| 运行环境 | Windows 个人计算机与普通摄像头 | 项目边界已明确；硬件规格待确定 | 摄像头兼容性、运行资源 |
| 语言与视频处理 | Python、OpenCV | 总体规划初选 | 摄像头读取、画面连续性、异常恢复 |
| 人脸检测 | YOLO 系列人脸检测模型 | **YOLO 在主链路中实际承担人脸检测为硬要求**；具体模型待选 | 模型来源与许可、测试场景效果、推理速度 |
| 面部关键点 | MediaPipe 等 | 候选方案 | 与 YOLO 人脸区域衔接、眼部关键点稳定性、失效识别 |
| 疲劳指标 | EAR、持续闭眼、PERCLOS | 指标方向已在规划中列出；参数未定 | 采样方式、观察窗口、阈值及正常眨眼区分 |
| 桌面界面 | PySide6 | 候选方案 | 视频刷新与推理并行时的界面响应、异常反馈 |
| 本地记录 | SQLite | 仅在 R08 纳入范围时选用 | 记录字段、查询与数据保存规则 |
| 实验材料 | 测试视频或标注样本，必要时使用 CVAT | 工具与数据来源待验证 | 使用许可、标注规则、可重复性、隐私处理 |

在 R02 的 Spec 前，应先查明可用 YOLO 人脸模型及其许可；在 R03/R04 前，明确人脸丢失、关键点无效、画面中多人时如何处理；在最终实验前，确定测试场景、人工标注依据和指标计算口径。准确率、帧率、报警响应时间及阈值不得凭规划文件虚设为已达到的数值，应根据目标设备和样本完成技术验证后写入对应 Spec。

## 5. 范围决策与当前限制

1. **待用户确认：**首轮是否以 F01—F08 为必做范围，并将 F09—F13 留作后续独立需求。
2. **待用户确认：**是否按上述建议将视频文件输入提前到 R02 之后、R03 之前；原规划将其列为 F12 增强项。
3. **待后续 Spec 明确：**摄像头与目标设备、多人画面处理、风险状态规则、声音行为、检测阈值和实验验收口径。
4. **仓库条件：**当前项目目录未发现独立 `.git` 仓库或业务源码。进入单项需求开发前，需确定项目仓库位置并按 `AGENTS.md` 的 `master` 分支规范建需求分支；不能把用户主目录的 Git 仓库误当成本项目仓库。
